# Benchmark run 1 — Kaggle 2× Tesla T4 (failed: GPU memory held by the embedding step)

- Notebook `kaggle/01_benchmark` at commit `01ea6e3` (standalone wheel) · 2026-10-28 10:35 UTC · 0.74 h
- llama.cpp `a7af149` (b11953) built; vLLM 0.32.0 installed
- Configurations: Qwen3-Coder-30B-A3B Q4_K_M and Devstral-Small-2-24B Q4_K_M on llama.cpp (4 slots × 16k),
  Qwen3-Coder-30B-A3B AWQ on vLLM (TP 2)

## What happened

1. Dense traceability: `Qwen/Qwen3-Embedding-0.6B` was loaded **in the notebook kernel** on GPU 0 and ran out of
   memory on its first batch (16 sequences of ≈ 1,500 tokens, fp32, eager attention: 12.5 GiB allocated).
   The error was caught, but the kernel kept 13.6 GiB of GPU 0 for the rest of the session.
2. Every LLM server then failed to load on GPU 0:
   - llama.cpp (both models): `cudaMalloc failed: out of memory` while allocating the model buffers;
   - vLLM: `Free memory on device cuda:0 (0.67/14.56 GiB) on startup is less than desired GPU memory
     utilization (0.9, 13.11 GiB)`.
3. Serving, LLM reranking, `oge eval` and the agent did not run.

The same configurations had loaded in the probe (`../probe/run2-2026-10-28.md`: 64k context ≈ 12.7 GiB per
GPU), which pointed to memory held by another process rather than to the configurations.

## What was still measured

Lexical traceability on Kaggle reproduces the local CPU result exactly (151 requirements × 3,261 tests):
BM25 MAP 0.488, graph 0.249, graph-constrained BM25 0.569 (`../traceability_lexical.json`).

## Fix (run 2)

- The embedding pass runs in a child process (`onprem_genai.knowledge.embed_job`): its GPU memory is returned
  when it exits, whatever happens; the notebook reads the vectors from the cache it wrote.
- Out-of-memory errors halve the batch (8 → 4 → 2 → 1) instead of failing the pass.
- Before each server start, `require_gpus_free()` waits for GPU memory to be released and otherwise fails that
  configuration immediately, naming the memory in use, instead of letting it fail later while loading.
